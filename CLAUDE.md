# vento-hotels

A world-class hotel management platform for Nigerian hotel groups and chains: reservations & front desk, booking engine & channel manager, guests & sales, restaurant & bar POS, housekeeping & maintenance, inventory & procurement, finance (multi-property, multi-entity, multi-currency), HR & payroll, guest app, executive analytics. Top-of-the-line UX, nothing extra.

Read before working:
- `docs/README.md` — the documentation map and the **definition of done for documentation**: a change isn't done until its docs are updated in the same commit.
- `docs/PRODUCT.md` — vision, personas, the ten modules and how they connect. Keep each module lean; don't add features outside it without asking.
- `docs/DOMAIN.md` — business vocabulary, statuses and rules.
- `docs/journeys/` — user walkthroughs on the demo hotel group; keep them true when behaviour changes.
- `docs/design/export/` — the approved designs (source of truth for UI); `docs/design/screen-inventory.md` maps them.
- `docs/decisions/` — why the big choices were made. Don't reverse one without a new decision record that supersedes it.
- `docs/ARCHITECTURE.md` — how the code is laid out and how a request flows.

## Stack
- **Monorepo:** pnpm workspaces + Turborepo — `apps/web`, `apps/api`, `packages/shared`
- **API:** Hono + oRPC on Node 24, contracts defined in `packages/shared` with zod v4
- **DB:** PostgreSQL + Drizzle ORM, migrations generated by drizzle-kit
- **Auth:** Better Auth with organizations (organization = the hotel group; it contains one or more properties and one or more legal entities)
- **Web:** Vite + React 19, TanStack Router (file-based), TanStack Query via the oRPC client, TanStack Table, react-hook-form + zod, shadcn/ui + Tailwind v4, Sonner, lucide, Recharts
- **Offline:** front desk and POS keep working through power and internet cuts — service worker + IndexedDB queue, synced with idempotency keys
- **Background jobs:** pg-boss (Postgres-backed queue) for night audit steps, ARI pushes, webhooks, messages, reports and scheduled checks. No Redis.
- **Files:** S3-compatible object storage (Cloudflare R2 in production, RustFS locally — see decision 0016) with signed URLs; guest ID images in a private bucket with short-lived links.
- **PDFs:** `@react-pdf/renderer` on the API for invoices, folios, registration cards, statements, payslips and board packs. Thermal receipts and kitchen tickets are 80mm print layouts (see `printing` skill).
- **Messaging:** email, SMS and WhatsApp each sit behind a provider interface (`EmailProvider`, `SmsProvider`, `WhatsAppProvider`); providers are open questions in `docs/DOMAIN.md`.
- **Observability:** structured logs (pino), Sentry for errors in web and api, uptime checks. Every request carries `organizationId`, `propertyId` and a request id in logs, never guest personal data.
- **Quality:** Biome (lint + format), Vitest, Playwright, GitHub Actions
- **Package manager:** pnpm only. Never npm or yarn.

## Commands
Requires Node 24 (`.nvmrc`) and pnpm (version pinned in `package.json`, enabled with `corepack enable`). Commands not built yet print which brick adds them. Biome lints and formats code and config, not Markdown.
- `pnpm install` — install all workspaces
- `pnpm dev` — run web + api (the API serves `/health` and `/rpc` on `API_PORT`, default 3000)
- `pnpm db:up` — start local Postgres and RustFS storage (Docker), waiting until healthy
- `pnpm db:down` / `pnpm db:reset` — stop them / delete their data and start fresh
- `pnpm db:status` — check the database and storage are reachable
- `pnpm db:generate` / `pnpm db:migrate` — create a migration from schema changes / apply migrations to the dev and test databases
- `pnpm db:studio` — browse the local database in Drizzle Studio
- `pnpm db:seed` — load the demo group (Kora Hotels Group, as in the designs and walkthroughs) for development, tests and sales demos
- `pnpm check` — Biome lint + format check (`pnpm check:fix` to apply fixes)
- `pnpm typecheck`, `pnpm test`, `pnpm e2e`
- Before any commit: `pnpm check && pnpm typecheck && pnpm test`

## Non-negotiables
1. **Organization isolation.** Every domain table has `organizationId` (FK, indexed, NOT NULL). Every query filters by the organization from the auth context, never from request input.
2. **Property scoping.** Operational data (rooms, reservations, folios, POS, housekeeping, stock) belongs to a property. Members can be limited to properties; the server enforces it on every query.
3. **Server-side authorization** per module × action in oRPC middleware. UI hiding is cosmetic only. Sensitive actions (rate override, discount, void, refund, room move after audit, comp) need the permission *and* a reason, and are logged.
4. **No overbooking by accident.** Availability changes (book, modify, cancel, channel sync) run in one transaction with row-level locking on the room-type inventory per date. Overbooking is only allowed up to a configured limit, explicitly.
5. **Money** is `numeric(14,2)` in Postgres, a string in TS, and calculated with the decimal helpers in `@vento/shared` (`dec`, `toAmount`, `money`, `percentOf`, `toNaira`, on decimal.js). Never floats; keep intermediate results as `Decimal` and round once, half-up, with `toAmount`. Store currency (ISO 4217, default `NGN`) beside every amount; foreign amounts also store the FX rate, its source and date. Folio postings and ledger entries are append-only (corrections are reversals with a reason) and the ledger must balance per entity.
6. **Business date.** Charges, revenue and reports use the property's business date, which only moves forward at night audit, not the wall clock.
7. **One source of truth for types:** zod schemas in `packages/shared`. Never redeclare an API type in `apps/web`.
8. **Lists are server-paginated** with the shared `{ items, page, pageSize, total }` shape.
9. **Multi-table writes** run in one transaction. Writes that can come from offline devices or webhooks are idempotent.
10. **IDs** are UUID v7. Every table has `createdAt` / `updatedAt`. Soft delete via `archivedAt` for master data (properties, rooms, rate plans, menu items, guests); hard delete is blocked when history exists.
11. **Secrets** never enter the repo (it is public). Use `.env` (git-ignored) and document keys in `.env.example`.
12. **Dates:** store UTC `timestamptz`; stay dates, business dates and due dates are `date` (no time) in the property's time zone (default `Africa/Lagos`).
13. **Statutory rules are data:** VAT, state consumption tax, service charge, levies, payroll deductions and similar rules live in versioned configuration with effective dates (and state where relevant), never in code constants. Check current Nigerian law before changing them.
14. **Guest data** follows the NDPA 2023: ID numbers encrypted at rest and masked in the UI, card data never touches our servers (provider tokens only).
15. **Everything is audited.** Every create, change, void, discount, override, room status change and sign-in writes an audit event (who, what, when, device, before/after, reason). Audit events are append-only and feed the leakage controls. Permission limits (e.g. max discount %) come from the permissions matrix in `docs/DOMAIN.md`, stored as configuration.

## Code style
- TypeScript strict, no `any`, no non-null assertions without a comment.
- Small files and functions. Comment *why*, not *what*.
- `@/` imports inside apps. Named exports, except route files.
- UI uses design tokens only (no hex in components), works in dark mode and at 375px width.
- Tests sit next to the code (`x.test.ts`); e2e lives in `apps/web/e2e`.

## Workflow
Feature: **product-manager** specs (`docs/specs/`) → **architect** plans → **backend** + **frontend** build (**payments** for folios, deposits, settlements and refunds, **finance** for night audit, ledger, tax, payroll and reporting, **distribution** for the booking engine, channel manager and rates) → **tester** covers → **reviewer** + **ui-designer** check → fix → commit.
**Bricks, branches and pull requests.** Work is built in small bricks, in the order of the release plan (`docs/PRODUCT.md`). Each brick gets its own branch (`stage-<n>/<short-name>`, e.g. `stage-0/monorepo-skeleton`), ends working and tested, and lands through a pull request that CI must pass and the owner merges. Never commit to `main` directly. One brick per pull request; don't start the next brick on top of an unmerged one unless asked.
**Attribution:** commits and pull requests carry no AI co-author or "generated with" lines.
Periodic and pre-release: **security** audits. Build, CI, deploys and monitoring: **devops**.
Project skills in `.claude/skills/` hold the step-by-step recipes (`add-module`, `add-list-page`, `db-migration`, `design-system`, `ux-writing`, `performance`, `offline-sync`, `printing`, `data-import`, `paystack`, `channel-manager`, `nigeria-compliance`, `testing-patterns`, `review-checklist`, `pre-commit-check`).
